# Безопасность выпуска

## Что является секретом

Полный снимок содержит базу 3x-ui, сертификаты, приватные ключи, токены, UUID, `sub_id`, параметры WireGuard/Reality и другие данные, достаточные для доступа к инфраструктуре. Незашифрованный `.tar.gz` нельзя публиковать даже в закрытом репозитории.

## Защита assets

- контейнер: `XUIBK01`;
- шифрование: AES-256-GCM;
- derivation ключа: PBKDF2-HMAC-SHA256;
- итерации: 600 000;
- отдельные случайные salt и nonce для каждого файла;
- проверка аутентичности при расшифровании;
- пароль отсутствует в контейнере, Git-истории, README, PR и release notes.

Репозиторий должен оставаться приватным, но приватность GitHub считается дополнительным слоем, а не заменой шифрования.

## Правила владельцу

- хранить пароль отдельно от GitHub минимум в двух защищённых местах;
- перед расшифрованием сверять SHA-256 `.xuibak`;
- расшифрованный `.tar.gz` хранить только временно и с правами владельца;
- не отправлять архив или пароль в issue, чат поддержки либо публичное облако;
- при подозрении на утечку считать секреты внутри снимка скомпрометированными и отдельно планировать их ротацию;
- не менять текущие пароли «для профилактики» в рамках восстановления: это отдельная операция с отдельным планом.

## Если пароль утрачен

Восстановить `.xuibak` без пароля невозможно по конструкции. Нельзя добавлять мастер-ключ или копию пароля в репозиторий. Пока сервер доступен, правильное решение — снять новый бэкап, выбрать новый пароль и проверить полную обратную расшифровку.

## Предпубликационная проверка

Перед каждым выпуском требуется поиск по добавляемым файлам на:

- реальные IP/имена узлов и SSH-пароли;
- PEM/OpenSSH/private-key заголовки;
- UUID, `sub_id`, полные subscription URL;
- bearer/API-токены;
- `.db`, `.sqlite`, `.key`, `.pem`, незашифрованные `.tar.gz`;
- случайно скопированные журналы и shell history.
