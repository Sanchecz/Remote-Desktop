# Инструкция для Codex: как обновлять и публиковать следующие версии

Этот runbook нужно дать Codex целиком при следующем обслуживании. Его цель — сохранить рабочие подписки Happ и не повторить регрессию Telegram/GEO-файлов.

## Неприкосновенные условия

Codex обязан:

- начать только с read-only диагностики;
- не менять SSH-пользователей, пароли или способ входа;
- не менять URL подписок, `sub_id`, UUID, клиентские ключи, публичные inbounds и назначения без отдельного прямого указания владельца;
- не выполнять `3x-ui` reinstall, очистку базы, массовое пересоздание клиентов или широкую перезагрузку сервера;
- не запускать `docker compose down`, cleanup или иные несвязанные действия;
- перед каждым изменением создать свежий переносимый снимок затрагиваемого узла;
- назвать точный изменяемый артефакт и путь отката до изменения;
- не публиковать IP, пароли, UUID, ссылки подписок, приватные ключи, базу SQLite или открытый `.tar.gz`;
- держать репозиторий приватным и отдельно подтвердить `isPrivate: true` до и после публикации.

## Порядок работ на серверах

1. Зафиксировать PID x-ui/Xray, состояние служб и таймеров.
2. Проверить SQLite `PRAGMA integrity_check` и число клиентов/назначений без вывода их секретных значений.
3. Проверить 10 существующих подписок: HTTP, непустое тело, одинаковый routing и интервал обновления 1 час. Не печатать URL в отчёт.
4. Проверить `xray-linux-amd64 run -test -c ...`.
5. Снять бэкапы на каждом узле:

   ```bash
   bash scripts/portable-backup.sh main
   bash scripts/portable-backup.sh node2
   ```

6. Проверить `tar -tzf`, `DB-INTEGRITY.txt`, `STATE.txt` и SHA архива.
7. Менять только согласованный параметр. Сразу после изменения повторить серверные тесты и проверить, что PID не менялся, если рестарт не требовался.
8. Для routing не добавлять `geosite:*`, `geoip:*` и внешние GEO URL без отдельного клиентского теста. Стабильная база `v1.0.0` имеет ноль таких ссылок.
9. Не включать периодические проверки, которые добавляют/удаляют inbound/outbound или иным образом меняют runtime рабочего Xray.
10. Попросить владельца проверить три обновления Happ, два повторных подключения, Telegram, `.ru`/`.рф`, один иностранный сайт и отсутствие ошибки ядра.

## Подготовка релиза

1. Извлечь routing из проверенной свежей SQLite-копии, а не брать старый локальный файл.
2. Сравнить SHA строки `happ://routing/add/...` на всех подписках.
3. Убедиться, что очищенный JSON не содержит IP серверов, UUID, паролей и subscription URL.
4. Зашифровать каждый полный архив:

   ```bash
   python3 scripts/backup_crypto.py encrypt input.tar.gz output.tar.gz.xuibak
   ```

5. Немедленно выполнить обратную расшифровку во временный файл и сравнить его SHA-256 с исходным `.tar.gz`.
6. Не помещать `.xuibak` в Git-историю. Загружать их только как assets приватного GitHub Release.
7. Обновить русские `README`, `RELEASE_NOTES`, `RESTORE`, `VALIDATION`, эту инструкцию и памятку владельца.
8. Пересобрать `SHA256SUMS.txt` и выполнить `scripts/verify_release.py`.
9. Просканировать весь добавляемый каталог на секреты и запрещённые типы файлов.

## Публикация GitHub

1. Проверить владельца и приватность репозитория через GitHub CLI/API.
2. Выполнить `git fetch origin --prune`.
3. Создать новую ветку от свежего `origin/main`, например `agent/3xui-happ-v1.0.1`.
4. Добавить только новый каталог `infrastructure/3x-ui-happ/vX.Y.Z/`.
5. Просмотреть `git status`, `git diff --check`, `git diff --stat` и полный staged diff.
6. Сделать один намеренный commit и push ветки.
7. Создать draft PR на русском; дождаться/проверить CI.
8. После проверок перевести PR в ready и слить в `main`.
9. Создать стабильный, не draft и не prerelease GitHub Release с новым уникальным тегом.
10. Приложить ZIP комплекта, оба `.xuibak` и отдельный `SHA256SUMS-release.txt`.
11. Повторно проверить приватность репозитория, статус релиза и доступность всех assets.

## Если работа прервалась

Codex должен сначала определить текущее состояние, а не повторять команды вслепую:

- посмотреть `git status` и уже существующие PR/release/tag;
- проверить наличие архивов и их SHA;
- проверить, не существует ли уже asset с тем же именем;
- не перезаписывать стабильный tag;
- не удалять старые бэкапы или ветки;
- продолжить с первого неподтверждённого шага.

## Критерий «готово»

Работа завершена только когда серверные и клиентские тесты пройдены, бэкапы проверены обратной расшифровкой, PR слит, релиз не является черновиком/предрелизом, репозиторий всё ещё приватный, а владелец получил ссылку и отдельный секрет расшифрования.
